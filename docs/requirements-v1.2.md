## 0. 設計哲学

### 0.1 このOSの存在意義

このOSは「情報提供」が目的ではない。  
目的はただひとつ：

**迷わず動ける状態を作ること**

AI動画SNS事業における実証済みの実績を、誰でも再現できる構造に落とし込み、  
FC展開・チーム拡大の基盤となる「再現性エンジン」として機能する。

---

### 0.2 このOSが守る7原則

#### 原則1. 次の1手しか見せない
人は情報量が増えるほど停止する。  
作業中に表示するのは「次の作業」と「必要最低限の情報」のみ。  
全体像は必要なときだけ開示する。

#### 原則2. 学習と実行を分離する
学習中に作業させない。作業中に学習させない。  
「理解するフェーズ」と「手を動かすフェーズ」は明確に分けて設計する。

#### 原則3. 毎回考えさせない
テンプレ化・DB化・再利用を前提とする。  
「また一から考える」が発生した時点でOSの設計が失敗している。

#### 原則4. AIを「答え」ではなく「改善装置」として使う
AIの役割は称賛ではない。  
差分分析と改善ループを高速化することである。  
AIの出力は「参考意見」であり、最終判断は常に人間が行う。

#### 原則5. 部分参加を前提とする
全体を理解しなくても部分参加できる設計にする。  
「必要な工程だけ渡す」ことで、FC・外注・チーム化すべてに対応できる。

#### 原則6. 継続できる設計にする
能力強化だけでなく、継続可能性を作ることがこのOSの役割である。  
人は論理ではなく感情で継続を決める。  
小さな完了体験を大量に作り、「今日はここまで」で止められる設計にする。

#### 原則7. 自走を最終目的とする
このOSの目的は、人を縛ることではない。  
監視によって動かすのではなく、自走によって動ける状態を設計する。  
最終目的は「OSなしでも回せる人を増やすこと」である。

---

### 0.3 このOSが扱う範囲 / 扱わない範囲

機能肥大化を防ぎ、OSとしての純度を保つために範囲を明示する。

| 扱う範囲 ✅ | 扱わない範囲 ❌ |
|-----------|-------------|
| AI動画制作フロー | 税務・法務 |
| 投稿運用・チェック | 高度なグラフィックデザイン制作 |
| データ分析・改善ループ | 人事評価・給与設計 |
| 勝ちパターンDB化 | 個別営業・クロージング |
| 再現性向上・テンプレ化 | プラットフォームのアルゴリズム予測 |
| FC向け教育・引継ぎ設計 | SNS以外の広告運用 |
| 作業ログ・時間管理 | 顧客管理（CRM） |
| ブランド世界観の再現 | コンテンツ以外のマーケティング全般 |

> **この範囲を超える要求が来た場合、OSに追加するのではなく外部ツールと連携する。**

### 0.4 AIとの関係原則

AIは高速化装置であり、思考停止装置ではない。  
特にFC化を前提とする場合、以下は必ず人間が行う判断領域として明記する。

**人間が行う判断（AI委譲禁止）：**
- 最終的な採用・不採用の判断
- ブランドの世界観・温度感・方向性の決定
- 윤리的判断・コンプライアンス確認
- 顧客理解・関係構築
- FC加盟者への最終評価

**AIが担う領域：**
- 台本の生成・添削・バリエーション展開
- データの差分分析・パターン抽出
- テンプレの提案・改善案の生成
- 作業の高速化・繰り返し処理の自動化

---

### 0.5 ブランド再現性の定義

このOSが再現すべきなのは「動画の作り方」だけではない。  
以下の要素すべてがブランド資産であり、再現の対象である。

| ブランド資産 | 内容 |
|------------|------|
| 世界観 | キャラ・ビジュアル・色調・構図の一貫性 |
| 温度感 | 話し方・言葉選び・フォーマル/カジュアルの基準 |
| テンポ | 動画の展開速度・カット数・情報密度 |
| 空気感 | BGM・効果音・フォントの統一感 |
| 言葉選び | NGワード・使う言い回し・ターゲットへの呼びかけ方 |

> FC展開において、加盟者が「同じ空気感」を出せるかどうかが  
> ブランド価値の維持に直結する。  
> ブランドDBはテクニックDBと同等以上の重要資産として扱う。

---

### 0.6 継続設計の原則

このOSは使われ続けなければ意味がない。  
継続は能力ではなく、設計で決まる。

**継続のための設計ルール：**

- 1STEPの作業時間を30分以内に設計する（長すぎる工程は分割する）
- 各STEP完了時に小さな完了演出を入れる（ログに残る・進捗バーが動く）
- 進捗を常に可視化する（今日は何%まで進んだか）
- 「途中保存」「今日はここまで」で止められる設計にする
- 連続失敗が続く場合はOSが「難易度を下げる提案」をする

> **完了体験の積み重ねが、OSへの信頼と継続意欲を作る。**

## 1. プロジェクト概要

### 1.1 目的

AI動画SNS事業における実務ノウハウを「誰でも再現できる仕組み」に落とし込み、  
FC展開・チーム拡大の基盤となるWebアプリを構築する。

### 1.2 現状の課題

| 課題 | 具体的な問題 |
|------|------------|
| 構造の属人化 | 現在の `index.html`（86,000文字超）は作成者しか把握できない |
| 導線の欠如 | 新規コンサル生がどこから始めるか迷う |
| ログ不在 | 作業時間が記録されずコスト計算・改善ループが回せない |
| 変更コスト | ツールリンク・工程内容がハードコードされており更新が困難 |
| 品質不足 | FC展開ツールとしての信頼性・プロダクト品質が不足 |
| ブランド再現の欠如 | 技術手順は存在するが、世界観・温度感の伝達手段がない |

### 1.3 このOSが解決すること

```
実績はある
  ↓
それを「仕組み」に落とし込む（技術＋ブランド両方）
  ↓
仕組みを「誰でも動かせる状態」にする
  ↓
OSなしでも自走できる人材が育つ
  ↓
FC展開・チームスケールが可能になる
```

## 2. ユーザー定義

### 2.1 ユーザータイプ（3種類）

| タイプ | 対象者 | 主な使い方 | UIスタイル |
|--------|--------|-----------|-----------|
| **作業者** | コンサル生・副業委託者 | 指定工程のみウィザード形式で実行 | ウィザード（完全誘導） |
| **運営者** | チームリーダー・中期担当 | チェックリスト＋工程進捗確認 | ハイブリッド（半自動） |
| **設計者** | かずさん・FC設計者 | 全工程俯瞰＋管理画面でカスタム | 俯瞰SOP＋管理パネル |

### 2.2 熟練度によるUI変化

| 熟練度 | UIモード | スキップ | 表示情報量 | 操作スタイル |
|--------|---------|---------|-----------|------------|
| 初級者 | 完全誘導 | 不可 | 最小限（次の1手のみ） | 押すだけ |
| 中級者 | 半自動 | 一部可 | 標準（現在STEP＋前後） | 選択あり |
| 上級者 | 高速実行 | 全て可 | 全体俯瞰 | ショートカット中心 |

### 2.3 ユーザーの特性

- 同一人物が複数タイプを兼ねる場合がある
- 上位階層が一部工程を切り出して下位者に委託する構造
- 上位階層の人が全画面を必要とするわけではない

## 4. 状態遷移設計

| 状態 | 意味 | 次の状態 |
|------|------|---------|
| `未開始` | 未着手 | → 作業中 |
| `作業中` | 実行中（開始時刻記録済み） | → レビュー待ち ／ 完了 |
| `レビュー待ち` | 作業完了・確認待ち | → 改善中 ／ 完了 |
| `改善中` | フィードバックを受けて修正中 | → レビュー待ち ／ 完了 |
| `完了` | 終了時刻記録済み・ログ出力可能 | → DB化済み |
| `DB化済み` | ナレッジDBへの記録完了・資産化 | （終端） |

## 5. 機能要件

### 5.1 Phase 1 最優先機能（A・B）

#### A. 作業ナビ機能（再現性）

**2段階ナビの流れ：**

```
[STEP開始]
  ↓
① 作業内容の確認画面
   - 工程名・作業説明・使用ツール・推定時間 を表示
   - 「開始する」ボタン → 開始時刻を自動記録・状態「作業中」へ
  ↓
② ツールリンク画面
   - 使用ツールのリンクボタン（別タブで開く）
   - 「作業完了」ボタン → 終了時刻を自動記録・状態「完了」へ
  ↓
③ 振り返り入力（任意）
   - 所感メモ（1行）
   - 改善点メモ（1行）
   - ブランドメモ（世界観・温度感で気づいたこと・1行）← 新規追加
  ↓
④ 完了演出 → 次のSTEPへ進む / 一時停止
```

## 6. 非機能要件

### 6.1 技術構成

| 項目 | Phase 1 | Phase 3（将来） |
|------|---------|---------------|
| フロントエンド | HTML / CSS / Vanilla JS | 同左 or React |
| ホスティング | GitHub Pages（無料） | 独自ドメイン＋CDN |
| データ永続化 | なし（メモリのみ） | バックエンドDB |
| 外部連携 | なし（TSV手動貼付） | Sheets API / Webhook |
| 依存ライブラリ | CDN経由のみ | 同左 |

### 6.2 ファイル構成

```
ai-video-os/
  ├── index.html        ← スタート画面（ユーザー名・プロジェクト・熟練度入力）
  ├── wizard.html       ← 作業ビュー（ウィザード形式・URLパラメータで工程切り替え）
  ├── ops.html          ← 運営ビュー（チェックリスト＋工程俯瞰）← Phase 2
  ├── admin.html        ← 管理画面（リンク設定・工程制御）← Phase 2
  ├── log.html          ← ログ確認・TSVコピー出力画面
  └── config.js         ← 工程定義・ツールリンク・熟練度別設定・ブランドDB
```

### 6.3 URLパラメータ設計

```
wizard.html?user=Aさん&project=instagram&steps=5-9&level=beginner
```

| パラメータ | 内容 | 例 |
|-----------|------|-----|
| `user` | ユーザー名 | Aさん |
| `project` | プロジェクト名 | instagram |
| `steps` | 表示するSTEP範囲 | 5-9 / 1-14 |
| `level` | 熟練度 | beginner / mid / pro |

### 6.4 デザイン方針

- 既存 `index.html` のデザイントークン・カラー体系を継承（SaaS Dashboard-Style）
- モバイル対応必須
- ダークモード固定
- 熟練度ごとに情報密度を変える
- 完了演出を必ず入れる（ログが積み上がる・進捗バーが動く）

## 8. ナレッジDB設計

作業ログは「経営データ」である。単なる記録ではなく、改善資産として蓄積・活用する。

### 8.1 技術DBカテゴリ

| DB名 | 内容 | 活用先 |
|------|------|--------|
| フックDB | 冒頭3秒の成功パターン | 台本生成・フック選択 |
| CTA DB | 行動喚起の成功パターン | 投稿設計 |
| 台本DB | 構成パターン・フレームワーク別 | テンプレ再利用 |
| **NG DB** | **失敗パターン・やってはいけない事例** | **再現性向上** |

### 8.2 ブランドDBカテゴリ（新規追加）

| DB名 | 内容 | 活用先 |
|------|------|--------|
| 世界観DB | 色調・キャラ・ビジュアル基準 | 画像生成・動画制作の統一基準 |
| 温度感DB | 言葉選び・NG表現・呼びかけ方 | 台本添削・ブランドチェック |
| テンポDB | カット数・展開速度・情報密度の基準 | 編集・動画生成の基準 |
| 空気感DB | BGM・効果音・フォントの統一ルール | 編集テンプレの基準 |

> **重要：** 成功だけ残すと再現性が弱い。  
> 失敗DBとNG DB こそが「普通の人でも一定成果を出せる」設計の核になる。

### 8.3 ROI設計（工程×収益の紐付け）

| 工程 | 計測指標 | 収益への影響 |
|------|---------|------------|
| 台本・フレーム選択（STEP5） | 制作時間 | 工数コスト |
| AI動画生成（STEP6） | 制作時間＋ツールコスト | 工数＋変動費 |
| 投稿（STEP8） | 再生数 | 流入量 |
| 投稿直後チェック（STEP9） | 保存率 | コンテンツ資産価値 |
| 分析（STEP10） | LINE登録数 | 導線効果 |
| 改善（STEP11） | 成約数 | 売上貢献 |
